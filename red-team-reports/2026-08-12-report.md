# Red Team: Rivet Ridge Rally — "MVP ready for beta testing"

## Verdict

The game is in better shape than its own July documentation suggests — it builds clean, runs without a single console error, and the rc.3 Canyon work is a real visual leap. But "ready for beta testing" is not a claim about the game; it is a claim about the *test*, and the test as currently configured cannot succeed. There is no URL to send testers to (hosting is an unresolved EXTERNAL BLOCKER in your own launch doc), and if testers somehow got the build, the shipped Support screen tells them — verbatim — "Public support contact: not published," while the runbook confirms "No client telemetry is included." A beta with no way in, no way to report out, and no way to observe play produces zero learnings at any level of game quality. Behind that sit two time bombs aimed specifically at beta testers: every byte of player data lives in evictable browser storage that Safari deletes after seven days of non-use (the game never requests persistence), and the mobile experience you're inviting phone users into has never once run on a physical phone. Meanwhile the one gate only you can close — the rc.3 owner visual review, packaged and waiting since August 9 — sits unsigned. The strongest honest case: this beta, launched today, fails not because the game is bad but because the beta apparatus doesn't exist yet. Roughly one focused week separates you from a beta that can actually teach you something.

## Scope and method

Target: the Rivet Ridge Rally working tree at commit `b2926d5` (version 1.0.0-rc.3), examined as an MVP entering beta. I read the governing docs (README, GAME_BIBLE, GAME_SPEC excerpts, LAUNCH_READINESS, QA_REPORT excerpts, OPERATIONS, the 2026-08-09 owner review package, ASSET_LICENSES), the core source (tracks, engine presentation route, menus/support screens, persistence), and the rc.3 review captures. I built the project in a clean environment (typecheck PASS, all 303 Vitest tests PASS, production build PASS) and played it headless in Chromium: boot → Rider School lessons 1–4 with real inputs → pause → skip → menu → Canyon Solo race. Zero console or page errors across the session. Note: this container renders WebGL in software, so nothing here evaluates real frame-rate or feel; performance claims below rest on the repo's own recorded evidence. Failure, for this review, means: the beta ships and returns nothing you can act on — or actively burns the goodwill of your first players.

## Findings

### [CRITICAL · confidence 9/10] The beta has no feedback channel and no instrumentation, so it cannot produce learnings

- **id:** no-feedback-channel-or-telemetry
- **Evidence in the target:** `src/ui/screens/MenuScreens.tsx:288` ships, in bold, "**Public support contact: not published.** The release owner must add a verified support address or URL before commercial launch. There is currently no authorized inbox for support, safety, privacy, or accessibility requests." Line 304: "**Accessibility contact: not published.**" Lines 341–344 render a player-visible "Launch blockers" panel with four rows marked "Blocked." `docs/OPERATIONS.md` (Support and incidents): "No client telemetry is included." There is no feedback button, form, or link anywhere in the UI. `LAUNCH_READINESS.md`: "Decision owner: Unassigned."
- **External evidence:** [Steamworks Playtest docs](https://partner.steamgames.com/doc/features/playtest) — Valve: "Collecting feedback from players is up to you. We've seen a number of developers include a big 'feedback' button right on the main menu of their game," routed to "a Steam forum… your discord channel, bug tracking software…". [GameAnalytics soft-launch guide](https://www.gameanalytics.com/blog/soft-launch-guide): soft launch exists to "collect data, identify bugs and receive early feedback from players," including whether "players are making it through the tutorial." [Game Developer, "6 steps to a successful playtesting process"](https://www.gamedeveloper.com/programming/6-steps-to-a-successful-playtesting-process-for-an-indie-developer) — Kiselev: "Testing results are collected through surveys with closed and open-ended questions, gameplay recordings…, automatic metrics…, and direct feedback." [Sentry docs](https://docs.sentry.io/product/): error monitoring exists so developers can "see what went wrong without asking 'can you reproduce that?'"
- **Why it matters:** The point of a beta is information. As shipped, a tester who hits a bug, loses a save, or bounces off Rider School has literally no path to tell you — the game itself tells them no channel exists — and you have no path to notice, because nothing is measured and errors die silently in their console. Every other finding in this report becomes undiscoverable through the beta itself. You get anecdotes from friends at best; the beta returns nothing, and the effort that produced 456 automated checks yields a test with a sample size of zero.
- **Fix:** Two days of work. (1) Pick one channel — a Discord invite or a hosted form — and put a Feedback button on the title screen and results screen. (2) Add a "Copy diagnostic info" button to the Support screen (version + commit + browser are already displayed; serialize them). (3) Add minimal, disclosed error capture — even a `window.onerror` ring buffer included in the copied diagnostics honors your no-tracking stance; hosted Sentry with a consent line is the stronger option your OPERATIONS doc already anticipates ("Any future analytics or error reporting needs a separate privacy… review"). (4) Write the five questions the beta must answer (fun? difficulty? art direction? school skip-rate? device coverage?) and name yourself the decision owner. Steam's pattern — big feedback button, one channel, stated questions — is the model.

### [CRITICAL · confidence 9/10] There is no way to get the game to testers: hosting is unchosen, and the obvious shortcut (itch.io) violates the app's own deployment contract

- **id:** no-hosting-or-distribution-path
- **Evidence in the target:** `LAUNCH_READINESS.md` External owner actions: "Production hosting, DNS/TLS, security headers, credentials, and deployment target — EXTERNAL BLOCKER — Owner-selected host, verified response headers, and tested immutable deploy/rollback procedure." `docs/OPERATIONS.md`: "The owner must add the host-specific upload, alias-switch, verification, and access-role commands here before public deployment." `README.md:71`: "Deploy `dist/` as one immutable unit at the root of a dedicated origin; do not deploy the Vite development server or mount the app below a URL prefix." The repo contains no deploy config of any kind (verified: no netlify/vercel/wrangler/CNAME files). The service worker (`shell-v35`) and offline mode assume an app-controlled origin.
- **External evidence:** [itch.io HTML5 docs](https://itch.io/docs/creators/html5) — official: "itch.io supports running HTML/JavaScript/CSS projects directly in the browser by embedding an `iframe` pointing to your uploaded code" and "Your project is hosted on a subdirectory on our HTML CDN" — i.e., precisely the URL-prefix, not-your-origin setup the README forbids; the docs say nothing about service workers. [itch.io SharedArrayBuffer announcement](https://itch.io/t/2025776/experimental-sharedarraybuffer-support) — leafo (itch.io founder) on their CDN domain changes: "If you have plays with save games stored in local storage, they will no longer be able to access them due to the domain change" — storage on a platform CDN is hostage to platform domain decisions.
- **Why it matters:** "Let's go" requires a URL today, and there isn't one. Worse, the path of least resistance — zip it onto itch.io tonight — quietly breaks the three systems the team spent weeks hardening: the service-worker offline shell (iframe + shared CDN subdirectory), the root-origin deploy contract, and IndexedDB persistence pinned to an origin you don't control. You'd be beta-testing a configuration the product explicitly doesn't support, and every offline/save bug report would be noise.
- **Fix:** One evening. Deploy `dist/` to a static host that satisfies the runbook as written — Cloudflare Pages, Netlify, or Vercel with a dedicated (sub)domain gives you the origin root, atomic immutable deploys, TLS, and per-path header control your own OPERATIONS checklist specifies (verify `nosniff`, `frame-ancestors`, and the hashed-asset/immutable vs shell/no-cache split it lists). Gate access with an unlisted URL for the closed beta. Keep itch.io off the table for this architecture unless you deliberately re-test SW + persistence inside it.

### [MAJOR · confidence 9/10] Every player's progress lives in storage the browser is allowed to delete — and on Safari, will delete after 7 days of non-use — with no persistence request and no warning

- **id:** evictable-local-saves-no-persist
- **Evidence in the target:** All progress, settings, custom tracks, and replays are IndexedDB-only (Dexie schema v6; "No account… or server dependency," README product scope). `navigator.storage.persist()` is called nowhere in the source (verified by search; the only "persist" hits are app-level retry code). The Support screen warns solely about *manual* clearing: "Clearing browser site data permanently removes local progress and tracks" (`MenuScreens.tsx:297`). Your own OPERATIONS severity table classes "widespread save loss" as P0.
- **External evidence:** [WebKit blog — Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/) — Apple, verified verbatim: ITP deletes "all of a website's script-writable storage after seven days of Safari use without user interaction on the site," explicitly including "Indexed DB… Service Worker registrations and cache"; home-screen web apps are exempt ("their own counter of days of use"). [web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web) — Google: best-effort storage "can be cleared by the browser without interrupting the user"; Chromium evicts "from the least recently used origin first" under pressure. [MDN — StorageManager.persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist): the API that requests the durable bucket.
- **Why it matters:** Beta cadence is exactly the trigger: an iPhone tester plays in week one, skips a week, returns — campaign progress, best times, and custom tracks are gone. To them it's a catastrophic save-loss bug (your own P0 class); to the beta it's poisoned feedback you can't even receive (finding 1). The game's most praiseworthy engineering — conflict copies, atomic writes, rebase-on-retry — all sits inside a bucket the platform treats as disposable.
- **Fix:** Half a day. Call `navigator.storage.persist()` after the first meaningful save and surface `navigator.storage.persisted()` state on the Support screen; on iOS Safari, show a one-time "Add to Home Screen to protect your saves" hint (the WebKit-documented exemption; note iOS has no install prompt API — [MDN PWA installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable): the `beforeinstallprompt` technique "is not supported on iOS"). Add the eviction caveat to the Support screen's honest-disclosure list, and nudge Track Builder users toward JSON export.

### [MAJOR · confidence 9/10] Mobile and cross-browser reality is 100% unverified: the game has never run on a physical phone, tablet, gamepad, or real Safari

- **id:** zero-physical-device-evidence
- **Evidence in the target:** `LAUNCH_READINESS.md` "Unverified physical and application environments" — every row UNVERIFIED: "Physical Android Chrome — Real touch, audio, storage, GPU, thermal, and battery session"; "Physical iPhone/iPad Safari — [same]"; "Actual Safari — Playwright WebKit is not equivalent"; physical gamepad; installed Firefox/Edge. All recorded performance evidence is one Apple M1 Max (desktop High 60.01 FPS; *emulated*-mobile Low 59.95 FPS) — a top-tier machine emulating a phone.
- **External evidence:** [CrazyGames technical requirements](https://docs.crazygames.com/requirements/technical/) — verified verbatim: "Games will be disabled on Chromium OS if they do not work smoothly on a 4GB RAM device"; gameplay reachable in "≤ 20 seconds"; "Game supports mouse, keyboard, and touch if mobile is supported." [Poki SDK requirements](https://sdk.poki.com/new-requirements): "Players on Poki play on a range of web connected devices. Make sure your game works on all of them!" — the floor the wider web-game market enforces before any player sees a game.
- **Why it matters:** You are inviting phone users into a build whose touch ergonomics, WebGL performance, thermals, audio unlock, and storage behavior on real hardware are collectively a guess. With a beta pool of a dozen people, a hard failure on iPhone Safari silently deletes half your sample on day one — and per finding 1 you wouldn't find out why. Your own docs are honest that "Playwright WebKit is not equivalent"; the market's platform gates (CrazyGames disables games that stutter on 4 GB devices) show how unforgiving real-device reality is.
- **Fix:** One hour before invites, run the full journey — cold load → Rider School lesson 1 → skip → Canyon Solo → save → kill tab → reopen offline — on your own iPhone (Safari) and one mid-range Android (Chrome), and note FPS feel, touch reach, heat, and audio. You own the "Physical/application test-matrix access" blocker row; this is its minimum viable closure, and it converts finding 3 and the touch-layout work from theory to evidence.

- **Evidence in the target:** `docs/OWNER_VISUAL_REVIEW_2026-08-09.md`: "READY FOR OWNER REVIEW… Nothing here is acceptance; no baseline has been promoted," with your signing procedure and 24-hour window spelled out. Verified on your machine today: `e2e/visual-regression.spec.ts-snapshots/` does not exist and no approval record exists — the visual-regression suite has no baselines. The package's own honesty section: "the hero remains flat solid-colour; the strengthened contract in `HERO_BIKE_RIDER_VERTICAL_SLICE.md` is **not** met by this package." The rc.3 midcourse captures (opened in this review) show five cube-bodied, box-headed rival riders — the pre-pivot style — flanking the detailed hero in every Rival race; your GAME_BIBLE forbids exactly this: "Avoid Roblox-adjacent block avatars, cube-first bodies… flat untextured blockiness as a final style," recorded after "the owner rejected the previous blanket acceptance."
- **External evidence:** None needed — the target convicts itself; the review package, bible, and captures are all repo artifacts opened this session.
- **Why it matters:** "MVP ready, let's go" and "my own review packet is unsigned since August 9" cannot both be true — either the visuals pass your bar (sign, promote baselines, and the regression suite finally has teeth) or they don't (then the beta's top question is art direction, and you should ask it deliberately). Separately: either schedule the rival-pack fidelity pass before beta, or make "do the rivals bother you?" an explicit beta survey question (which requires finding 1's channel).

### [MAJOR · confidence 7/10] First boot front-loads a 12-lesson + 2-drill school before the first real race — the design research says simple-game tutorials don't earn their cost

- **id:** front-loaded-14-step-tutorial
- **Evidence in the target:** Played this session: a fresh profile boots directly into Rider School — "FIRST RIDE · 12 LESSONS + 2 CONTACT DRILLS" — with a large "START LESSON 1" button and a visually de-emphasized "Skip training" link (screenshot `rt-shots/01-title.png`); a first-time visitor never sees the title menu or track list first. Lessons gate on fresh evidence ("an earlier lane move… cannot clear a later lesson," GAME_BIBLE), and the sub-3-minute completion claim is a measured optimal path; real novice duration is unknown — and unmeasurable (finding 1).
- **External evidence:** [Andersen et al., CHI 2012, University of Washington PDF](https://grail.cs.washington.edu/projects/game-abtesting/chi2012/chi2012.pdf) — 45,000-player study, verified verbatim: "Although tutorials increased play time by as much as 29% in the most complex game, they did not significantly improve player engagement in the two simpler games… investment in tutorials may not be justified for games with mechanics that can be discovered through experimentation." [Game Developer — "How to train players right"](https://www.gamedeveloper.com/design/how-to-train-players-i-right-i-so-they-don-t-hate-learning-to-play) — Stout names the canonical complaints: "Training wastes the player's time!… Training is forced on the player!" [GameAnalytics-derived 2025 benchmarks](https://gamedevreports.substack.com/p/gameanalytics-mobile-gaming-benchmarks): median mobile session 5–6 minutes; top-25% D1 retention 26–28%. Player sentiment, verbatim: "I have stopped playing plenty of games because I can't skip the tutorial. Forced tutorials are the worst" ([NeoGAF thread](https://www.neogaf.com/threads/i-just-found-out-skipping-tutorials-is-common-in-gaming-do-you-why-or-why-not.1678529/)).
- **Why it matters:** A median first session is 5–6 minutes; the school can consume all of it before a player touches an actual race (3–4.5 minutes each). Your core mechanics are semi-conventional (accelerate/steer) with a genuinely novel layer (heat/pitch/barriers) — the Andersen result says the conventional part teaches itself through play, and your own bible's pillar is "generous enough for a new player to finish a first race." Counter-evidence, stated honestly: the skip IS offered on the first card, the lessons are interactive riding rather than text, and heat/wheelie rules are the "complex" case where Andersen found tutorials help — this is why confidence is 7, not 9.
- **Fix:** Cheapest: make "Skip training" a peer-sized button and put a "Rider School (recommended)" card on the title screen instead of auto-entering it; teach heat/cooling with two just-in-time toasts in the first Practice race. Alternatively keep the current flow but make school-skip-rate and school-abandon-point the beta's first measured questions (requires finding 1). Moto X3M — the genre's browser incumbent, [4.3★ from 5.2M votes on Poki](https://poki.com/en/g/moto-x3m) — teaches everything in-level with zero front-loaded school.

### [MAJOR · confidence 7/10] The retention loop is a bet against the whole market — and the beta can't measure whether the bet works

- **id:** no-retention-loop-vs-market
- **Evidence in the target:** First-clear content is ~19 minutes of solo-target racing (targets 190+208+224+239+259 s) plus rival races and seven Summit tiers — under an hour for a competent player. By explicit design there are no leaderboards, no multiplayer, no accounts, no public track sharing ("Out of scope for RC1," GAME_BIBLE; "No account, payments, ads, tracking, public sharing, or server dependency," README). The Track Builder — the one renewable-content system — can only export/import JSON files locally.
- **External evidence:** The top comparable titles all retain through what RRR excludes, per their official pages opened this session: [Smash Karts on Poki](https://poki.com/en/g/smash-karts) (top 3D browser racer, 4.4★/1.5M votes) — multiplayer modes, XP leveling, "over 30 Season Levels" of seasonal rewards; [Mad Skills Motocross 3 on Google Play](https://play.google.com/store/apps/details?id=com.turborilla.bike.racing.madskillsmotocross3&hl=en-US) (50M+ downloads) — "Compete in a variety of multiplayer and pvp modes," "new offroad tracks added every week," leagues; [Moto X3M on Poki](https://poki.com/en/g/moto-x3m) — 50 levels and sequels. Sentiment from the closest solo-dev analogue, slowroads.io ([HN thread, 760 points](https://news.ycombinator.com/item?id=33305234)): praise for frictionless polish, and the recurring gap — "If anyone is looking for this but as a more complete game, check out art of rally."
- **Why it matters:** This is a considered privacy-first stance, not an oversight — but it removes every mechanism the market demonstrably retains players with, and leaves mastery-of-five-tracks as the whole loop. For the beta specifically, the compounding problem is epistemic: with no telemetry (finding 1) you cannot observe D2/D7 return, so the single most important commercial question — "do people come back?" — is unanswerable by this beta. The bet may be right (slowroads thrived on feel alone); as configured, you'll never know.
- **Fix:** Beta-scoped: put "did you come back the next day, and what for?" in the survey; watch persistence via the feedback channel. Product-scoped, server-less options consistent with your stance: shareable track *codes* (the validated JSON already exists — compress to a copy-paste string), local ghost/replay racing against your own PBs (replay codec already ships), and a visible per-track medal ladder. Name the choice explicitly rather than inheriting it.

### [MINOR · confidence 8/10] The repository has no product license, no operator identity, and open trademark/AI-provenance reviews — acceptable for a closed beta, untenable one step beyond it

- **id:** no-license-or-operator-identity
- **Evidence in the target:** No `LICENSE` file exists (verified; `ASSET_LICENSES.md` is an inventory, not a grant). `LAUNCH_READINESS.md` External owner actions: "Top-level product license — EXTERNAL BLOCKER"; "Final trademark, trade-dress, copyright, and generated-output review — EXTERNAL BLOCKER"; "Generated-image account/agreement provenance — EXTERNAL BLOCKER" (the shipped title art and panorama are OpenAI-generated; "account/session receipts are not stored in the repository," ASSET_LICENSES). The Support screen publishes no operator identity — by admission.
- **External evidence:** [choosealicense.com/no-permission](https://choosealicense.com/no-permission/) — GitHub, verified verbatim: with no license "the work is under exclusive copyright by default" and "nobody else can copy, distribute, or modify your work without being at risk of take-downs, shake-downs, or litigation." [itch.io creator docs](https://itch.io/docs/creators/download-keys) show the standard restricted-access patterns betas use instead of public posting.
- **Why it matters:** For a hand-picked closed beta over a private URL, practical risk is low — which is why this is MINOR, not inflated. But the moment a tester shares the link (they will), you are distributing an unlicensed work with no stated terms, no operator, and an unreviewed trademark ("Rivet Ridge Rally" has had no clearance search recorded anywhere in the repo). Your own launch doc already knows all of this; the risk is drift from "closed beta" to "public link" without the paperwork ever catching up.
- **Fix:** One hour now, counsel later: choose the license (choosealicense.com walks it), add a three-line beta notice to the Support screen (who operates it, beta status, feedback channel — which finding 1 creates anyway), and keep the URL unlisted until the trademark search and AI-art provenance row are closed.

## Untested hypotheses

These did not meet the evidence bar this session; each comes with its test.

1. **Real-device performance may miss budgets on mid-range phones.** My environment renders WebGL in software (~1 FPS — meaningless as evidence), and the repo's only numbers are M1 Max. Test: finding 4's one-hour device pass with the FPS overlay on.
2. **"Rivet Ridge Rally" may have trademark conflicts.** No USPTO/EUIPO search was performed this session (confidence n/a). Test: run a knockout search before public naming investment; your launch doc already gates on it.
3. **Novice tutorial duration may far exceed 3 minutes.** The <3 min figure is a measured optimal path; no human-novice timing exists. Test: watch two first-time players (NN/g: ["testing no more than 5 users"](https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/) per round) or measure via the beta once finding 1 lands.
4. **True multi-tab concurrency remains unverified** (the repo says so itself). Low beta impact; test with two tabs racing + editing per the QA report's open scope.

## What survived

The engineering culture is the strongest I've red-teamed at this scale of project: every claim in the repo is scoped, dated, hash-bound, and honest about its own limits — the review process found *zero* instances of evidence inflation, and my independent build/test/play run confirmed the automated story (typecheck, 303 tests, clean boot, zero console errors). The data-safety engineering (conflict copies, atomic quarantine, rebase-on-retry, bounded imports) is production-grade. Accessibility breadth — reduced motion/shake, high contrast, captions, full remapping, mirrored touch, 44px targets, semantic touch buttons — exceeds most shipped commercial games. The rc.3 Canyon visual work is a genuine leap over July's captures; the Track Builder is a real product asset; and the original-IP discipline (Excitebike *inspiration*, zero Excitebike *expression* — the lane/heat lineage is documented on [Wikipedia](https://en.wikipedia.org/wiki/Excitebike) while every asset is provenance-tracked original) is exactly right. None of this changes the verdict, because none of it is what this beta will live or die on.
